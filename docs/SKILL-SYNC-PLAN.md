# Skill ↔ TCC data-format sync — implementation plan

Written 2026-07-29 after an audit of both repos. Supersedes the field-level asks in
`SKILL-CHANGE-REQUESTS.md` where the two disagree; each SCR closed by this plan is named below.

**Framing (unchanged, from TCC-TZ §7):** the skill owns every schema and is the only writer; TCC is
a consumer and the process front-end. Backward compatibility with existing ledgers is explicitly
**not** required — the only ledgers on disk are two hand-edited dogfood files, migrated by a
one-shot script.

## 0. Decisions taken (2026-07-29, with the user)

| # | Question | Decision |
|---|---|---|
| D1 | Project layout | `<project>/state/<preset>/v_NNN.json` — already TCC's `config.state_root()` default and the skill's existing shape. **TZ §3's `presets/<preset>/state/` is dropped**; TZ gets edited to match the code. |
| D2 | Project facts file | **One `project.json`, written by the skill.** `project_profile.json` is retired; TCC reads its left-panel sections out of `project.json`. Closes SCR-011/015/016 with one file. |
| D3 | EQ representation | **Structured bands**: `{"i":1,"type":"PK","f":1000,"gain_db":-9,"q":2,"bypass":false}`. The string form (`"PK 1000 -9 Q2"`) becomes display-only, generated by a skill helper. TCC deletes `EqBand.from_string`. Closes SCR-006. |
| D4 | Virtual/other tiers | **The apply gate becomes tier-aware.** A delta may address any profile-declared tier; a flat delta still means `channels`. `validate`/`diff`/`render`/settings-sheet all cover every tier. |

Canonical layout:

```
<project>/                          # git repo
  project.json                      # machine facts: car, equipment, per-channel driver, glossary,
                                    #   dsp hardware controls, param sections, _open_questions
  dsp_profile.json                  # DSP capability profile (tiers + field vocabulary)
  autosound_context.md              # prose for the human/Critic; generated where it overlaps
  preference-profile.md
  process/
    process-state.json              # current slice        (schema_version 1, exists)
    journal.jsonl                   # append-only events   (exists)
  state/
    registry.json                   # active preset/slot
    <preset>/v_NNN.json + HEAD      # ledger (schema_version 2, this plan)
  target-curves/
    registry.json                   # active curve + curve↔preset (SCR-009)
    <name>/…
  rew_analitic/                     # exports/, dsp-config/, *.mdat (gitignored)
```

Env vars converge on the skill's names: `AUTOSOUND_PROJECT_DIR` (project folder) and
`AUTOSOUND_STATE_ROOT` (ledger root override, defaults to `<project>/state`). The
`AUTOSOUND_TCC_*` spellings are removed from TCC.

## 1. The finding that matters most

**The schema landed; the writing discipline did not.** `naming.py`, `state/process.py` and the
ledger-schema branch all exist and TCC already consumes them — but no prose in the skill tells the
Generator to use them. `SKILL.md:43` still resolves the phase by reading the `▶️ CONTINUE` block of
`tuning-changelog`; no `.md` in the skill mentions `process-state.json`, `glossary.json` or
`project.json`. In a real session TCC would therefore find nothing to render.

Everything in §2 below is plumbing; **§3 is what makes the plumbing carry water.** Do not ship §2
without §3.

Second-largest finding: the ledger's writer knows exactly one tier. `validate()` checks only
`channels`; `virtual_channels` is unvalidated passthrough and `apply.propose`/`diff`/`render` cannot
touch it. The skill physically cannot bank a change to a virtual channel that the GUI displays —
the tier exists in `data/private/state/{FULL,SQ}/v_001.json` only because those files were
hand-edited.

## 2. Skill-repo work (`autosound-tuning-skill`)

Branch off `feat/tcc-ledger-schema` (its one commit is a prerequisite and is not yet in `main`).

### 2.1 Ledger schema v2 — tier-aware (P0) · closes SCR-002/003/005/006, D3, D4

`rew_tool/state/state.py`, `apply.py`, `schema.md`.

1. **`schema_version: 2`** top level, written by `snapshot()`, required by `validate()`. Export
   `SCHEMA_VERSION` from the module so a consumer can compare rather than guess.
2. **Legalize the top-level keys real ledgers already carry** and `schema.md` omits: `features`,
   `slot_label`, `save`, `virtual_eq_ptr`, plus every tier key.
3. **Tier convention, made explicit in code** (TCC already assumes it —
   `state/dsp_state.ProjectView.from_dict`): profile group `physical_outputs` → the ledger's
   `channels` key; every other group id → a same-named top-level key. Put this in one place,
   e.g. `state.tier_key(group_id)` / `state.tiers(state)`, and have both repos call it.
4. **`validate(state, profile=None)`**: `channels` keeps today's strict rules. Other tiers are
   validated against the profile's declared `fields` when a profile is passed (a virtual channel
   has no `hp`/`lp` and must not be required to), and type-checked generically when it isn't.
   Keep the existing optional-field type checks (`order` int, `mute`/`off`/`hidden` bool).
5. **Structured EQ** (D3): `eq` is a list of band objects. Validate `type ∈ {PK,LSH,HSH,APF1,APF2}`,
   `f > 0`, numeric `gain_db`/`q` where the type takes them, `bypass` bool, optional 1-based `i`.
   Add `eq_band_str(band)` / `eq_str(bands)` helpers for the settings sheet, chat output and the
   Helix export path.
6. **Tier-aware apply gate** (D4): `apply.propose(h, delta)` accepts either the flat form (`channels`,
   unchanged, so existing call sites keep working) or a tier-keyed dict. Deterministic refusals
   (unknown tier, unknown channel, unknown field, samples-not-ms) extend to every tier. `diff`,
   `render` and the settings sheet must show virtual-tier changes — a silently dropped virtual gain
   change is exactly the split-artifact bug the ledger exists to prevent.
7. **Migration script** `rew_tool/state/migrate_v2.py` — v1 → v2 for the two dogfood ledgers:
   inject `schema_version`, convert `eq` strings to band objects, leave everything else.
8. Extend `state.py selftest` to cover: a virtual-tier propose→attest round trip, an EQ band
   round trip (`eq_str(parse) == original`), and a v1→v2 migration.

### 2.2 `rew_tool/project.py` — the project-facts module (P0) · closes SCR-001/011/014/015/016/017

New stdlib-only module + `project-schema.md`, same shape as `state/process.py`:

- **Read/write/validate `project.json`**, `schema_version: 1`. Sections:
  - `car`, `source`, `dsp` (vendor/model → links `dsp_profile.json`), `amps`, `mic`, `paths`,
    `presets`;
  - `channels[]` — per output channel: `code`, `slot`, `descr`, `role`, `order`, `driver`
    (make/model), `fs_hz`, `impedance_ohm`, `hidden` (SCR-001/003);
  - `glossary` — the SCR-008 shape `naming.Glossary.for_project` already reads (keep the
    standalone `glossary.json` path working as the alternative);
  - `hardware` — DSP-level facts constant across presets: `{"controls": {"RearRC": "3/4",
    "SubRC": "-4dB", "RealCenter": "ON"}}`. **This resolves SCR-017**: these are knob positions on
    the device, not per-preset state, so they leave the ledger. `dsp_profile.json` declares which
    controls a given DSP has (absent for MUSWAY et al. — never assumed universal). Per-preset stays
    per-preset: `mute`, `off`.
  - `param_sections` — the left panel's Project/System/Car-audio-analysis content (D2), same
    `[{id,label,params:[[k,v]]}]` shape TCC's `load_param_sections` already parses, so TCC only
    changes *which file* it opens;
  - `channel_summary` — e.g. `{"virtual": {"total": 8, "off": 1}, "outputs": {"total": 12,
    "off": 2}}` (SCR-016), written by intake, not re-derived by TCC.
- **Provenance + open questions** (SCR-014): every fact may carry `{"value":…, "source":
  "user|measured|datasheet", "at": …}`; unknowns go to `_open_questions`, never guessed. Reuse the
  `dsp_profile.py` convention rather than inventing a second one.
- **`config_change` events**: `project.record_change(process, file, what, why, source, impact)`
  writes the journal event SCR-014 specifies, with `impact ∈ {none, "remeasure: [codes]",
  full_rebaseline}`. This is what lets TCC gray out stale measurements and the skill re-propose
  exactly the affected captures on resume.
- **CLI** (`python rew_tool/project.py <project-dir> show|check|set …`) — the TZ §7 test: a solo
  tuner in a terminal must have a use for it.

### 2.3 `rew_tool/contract.py` — one whole-project checker (P0)

The single deliverable both repos key off. `python rew_tool/contract.py check <project> [--json]`
walks every machine file, reports per file: exists · `schema_version` · valid · issues; plus
cross-file checks (glossary codes vs ledger channels vs REW titles via `naming.validate_series`;
`process-state` done steps with missing evidence via `unevidenced_done_steps`; ledger tiers vs
profile groups). Human output for skill sessions, `--json` for TCC's diagnostics panel (TZ §8's
"what TCC found on disk, what's missing", currently spilling into the dialog as system bubbles).

Also export a `CONTRACT` table (file → owner → schema version) from one place, so a version bump is
a one-line change both sides read.

### 2.4 Writing discipline in the prose (P0) — **the part that makes it real**

- **`SKILL.md`**
  - Rewrite the Pre-Session/Resume step: reconcile from `process/process-state.json` **first**
    (`python rew_tool/state/process.py show`), then the ledger HEAD, then prose. Drop
    "read the ▶️ CONTINUE block" as the primary phase source.
  - New guardrail: *the process is written as it happens* — `enter_phase` on every phase change,
    `add_step`/`start_attempt`/`finish_step` as the plan moves, `record_reviewer` after every
    Critic call. `finish_step` without evidence is refused by code, and that is the point.
  - Guardrail: *machine files are the truth, prose is generated* — `dsp-state-current`,
    `tuning-changelog` and `audit-trail.md` are views (closes SCR-007).
- **`references/phases/phase_-1_intake.md`** — intake's deliverable is no longer only prose: it
  writes `project.json` (incl. glossary + per-channel drivers + hardware controls + channel
  summary), `dsp_profile.json`, and seeds the first ledger snapshot with **every tier populated**.
  Unknowns → `_open_questions`.
- **`references/core/naming-and-structure.md`** — §3 points at `naming.py` as the implementation,
  §4a/§5/§6 at the canonical layout above and at `target-curves/registry.json`.
- **`references/core/process-control.md`** / `process-phases.md` — phase transitions go through
  `process.py`.
- **`references/core/data-contract-universal.md`** — add the machine-file contract table (owner,
  path, schema version, writer) mirroring §2.3's `CONTRACT`.

### 2.5 Second-tier items (P1)

## 3. TCC-repo work (`autosound-tcc`)

Each item is small and follows the skill; land after the corresponding skill change and bump the
submodule pin.

1. **`core/config.py`** — drop `AUTOSOUND_TCC_STATE_ROOT`/`AUTOSOUND_TCC_PROJECT_DIR` in favour of
   `AUTOSOUND_STATE_ROOT`/`AUTOSOUND_PROJECT_DIR`; `project_profile_path()` is deleted (D2).
2. **`state/dsp_state.py`** — delete `EqBand.from_string` and `parse_eq_bands`'s string path; read
   band objects (D3). `load_param_sections()` reads `project.json`'s `param_sections`. Import the
   tier-key convention from the vendored `state.py` instead of hard-coding it in `from_dict`.
3. **New `state/project_view.py`** — read `project.json`: System params, Project params (incl.
   `channel_summary`), Car-audio-analysis sections, `_open_questions` as onboarding TODO chips
   (SCR-014/015/016). Replaces the current static placeholders.
4. **`ui/tcc/dsp_tree.py`** — `tag`/`tag_value` chip reads `project.json`'s `hardware.controls`
   (SCR-017); the ledger keeps only per-preset `mute`/`off`.
5. **`core/vendor_loader.py`** — register `state/project.py` and `contract.py`.
6. **Diagnostics panel** — render `contract.py check --json` (TZ §8), instead of system bubbles in
   the dialog.
7. **Version guard** — on project open, compare each file's `schema_version` against the vendored
   `CONTRACT` and show a clear "skill submodule is older/newer than this project's data" banner
   rather than mis-rendering.
8. **`core/mcp_server.py::report_phase`** — today it records phase/step into TCC's own session
   registry, which is a second process-state. Once the Generator writes `process/` itself, this
   tool should either be removed or become a thin read-back; TCC must not become a parallel writer.
9. **`docs/TCC-TZ.md` §3** — edit the layout to D1; **`docs/SKILL-CHANGE-REQUESTS.md`** — mark
   SCR-001/002/003/005/006/007/009/010/011/013/014/015/016/017 as `accepted` pointing here, and
   SCR-012 as `rejected` (TZ §7).
