# LangGraph Integration Concept for TCC

> **Document Status:** Architecture Proposal / Decision Record.  
> **Goal:** Replace the complex and parser-heavy `Claude Agent SDK` with a local, deterministic, and native Python framework—**LangGraph**—fully integrated into the Qt (PySide6) desktop application without unnecessary protocols or microservices.

---

## 1. Background & Problem

The current approach of using assistant-SDKs (including Claude Agent SDK) inside a native desktop GUI leads to several friction points:
* **Text "Noise":** The model outputs internal Chains of Thought, raw tool calls (XML/JSON), and service tags that look like clutter in a chat window.
* **Complex Parsing:** Requiring heavy regex or custom parsers to extract useful UI updates from the token stream.
* **Vendor Lock-in:** Tied to specific provider formats, contradicting the *provider-agnostic* goal.

---

## 2. LangGraph as the Native Orchestrator

**LangGraph** acts as the sole local orchestrator (the "brain") inside the main Python process of TCC.

1. **No Separate Servers or MCP for UI:** LangGraph runs in the same Python memory space as the Qt windows.
2. **Structured State:** The graph operates on clean Python TypedDicts that mirror our `process-state.json` and ledger.
3. **Native Human-in-the-Loop:** Using built-in interrupt mechanisms, the graph pauses before any destructive action and awaits user confirmation via UI buttons.

---

## 3. UI Update Strategy (Signals vs. File Watcher)

* **PySide6 Signals (Active Channel):** Graph nodes emit structured events (Python Dicts) during execution. A worker wrapper using `qasync` performs standard `emit()` calls via Qt Signals.
* **File Watcher (Passive Channel):** A `QFileSystemWatcher` monitors the project folder for external terminal changes.

---

## 4. Key Benefits

1. **Provider-Agnostic:** Swap Claude for OpenAI, local Ollama, or Gemini easily.
2. **Clean UI:** Consumes clean events instead of raw token streams.
3. **Robust Safety Gates:** Hard guardrails enforced inside Python function logic.
4. **Permissive Licensing:** Distributed under the **MIT** license.

---

## 5. Migration Roadmap

1. Define Graph State Schema.
2. Wrap Existing Tools with `@tool`.
3. Implement Async Qt Bridge (qasync).
4. Implement Arbiter Interruption Node.

## 1. Передумови та проблема
Поточний підхід із використанням асистент-SDK (включно з Claude Agent SDK) усередині десктопного GUI призводить до таких труднощів:
• Текстове «сміття»: Модель видає внутрішній Chain of Thought (роздуми), сирі виклики інструментів (XML/JSON), які у вікні чату виглядають як каша.
• Складна обробка: Необхідність писати складні регекси або парсери для виділення корисних даних із потоку токенів.
• Закритість екосистеми: Залежність від специфічних форматів одного провайдера, що суперечить принципу provider-agnostic (Варіант C з нашого ТЗ).

## 2. Що таке LangGraph у цій архітектурі
LangGraph стає єдиним локальним оркестратором (мозком) усередині основного Python-процесу TCC.

```text

[ Користувач / UI (PySide6) ] 
       │ (Клік / Повідомлення)
       ▼
[ Qt Signals / Slots ] ◄──────────► [ LangGraph (Python Core) ]
                                          │
                   ┌──────────────────────┼──────────────────────┐
                   ▼                      ▼                      ▼
           [ Generator Node ]     [ Critic Node ]       [ Tool Nodes ]
              (Claude API)         (Gemini CLI)          (REW API / Python)
                   │                      │                      │
                   └──────────────────────┴──────────────────────┘
                                          │
                                          ▼
                            [ Диск: Файли та Леджер ]

```

1. Жодних виділених серверів чи MCP для UI: LangGraph працює в тому ж просторі пам'яті Python, що й Qt-вікна.
2. Структурований стан (State): Граф оперує чіткими Python-словниками або датакласами (які повністю мапляться на наш process-state.json та леджер).
3. Нативна підтримка Human-in-the-Loop: Завдяки вбудованим механізмам пауз (interrupt), граф зупиняється перед будь-якою деструктивною дією (наприклад, пропозицією еквалайзера) і чекає на підтвердження від користувача через кнопку в інтерфейсі.

---

## 3. Як вирішується задача оновлення UI (Signals vs. File Watcher)
Архітектура використовує комбінований підхід, який задовольняє як потреби інтерактивної сесії, так і роботу зовні:
• Сигнали PySide6 (Активний канал для сесії): Вузол графа під час виконання генерує не сирий текст, а структуровані події (Python Dict). Потік виконання через обгортку qasync або QThread робить emit() за допомогою стандартних Qt Signals. Інтерфейс миттєво малює красивий бабл чату або системний чіп події.
• File Watcher (Пасивний канал для синхронізації): Зберігається QFileSystemWatcher на папку проєкту. Якщо користувач запустив паралельно термінал (або працював у режимі view), зміни у файлах леджера чи process-state.json миттєво підтягуються в інтерфейс. Також залишається кнопка ручного оновлення («Оновити»).

---

## 4. Переваги переходу на LangGraph
1. Повна незалежність від провайдера (Provider-Agnostic): Сьогодні у вузлі генератора стоїть Claude, завтра за пару рядків коду можна підключити OpenAI, локальну модель через Ollama або Gemini.
2. Чистий UI без артефактів: Інтерфейс отримує події типу {"event": "tool_success", "tool": "rew_measure"} замість тисяч символів службового коду моделі.
3. Надійні гейти безпеки: Захист від «дурня» чи небезпечних налаштувань зашитий у логіку Python-функцій (Tool Nodes), а не залежить від того, чи дослухається модель до промпту.
4. Ліцензійна чистота: Бібліотека розповсюджується за ліцензією MIT, що ідеально сумісна з відкритими компонентами TCC.

Шлях 2: Через Qt Signals (Активний, для стрімінгу чату)
Для речей, які не пишуться у файли (наприклад, проміжні думки моделі, бабли чату, або запит на підтвердження від Арбітра), LangGraph працює через події.
1. LangGraph працює у фоновому потоці (QThread).
2. Коли вузол закінчує роботу (або інструмент повертає результат), граф генерує подію (Python Dict).
3. Твій фоновий потік ловить цю подію і робить emit() через стандартний pyqtSignal(dict).
4. Головний потік Qt ловить сигнал і малює новий бабл або попап "Підтвердіть зміну EQ".

## 1. Проблематика та передумови

Під час проєктування AI-асистентів для десктопних застосунків розробники часто зіштовхуються з двома критичними бар'єрами:
1. **Фінансовий бар'єр (Pay-as-you-go шок):** Стандартні бібліотеки інтеграції (на кшталт прямих викликів API Anthropic чи OpenAI) вимагають покомлавової оплати за токени. Для пет-проєктів або проєктів із фіксованим циклом розробки на 1-2 місяці це створює психологічний і фінансовий дискомфорт (особливо при тестуванні та помилкових запитах).
2. **Проблема контексту:** ШІ утиліти не повинні «забувати» історію налаштувань акустичного процесу впродовж активної фази.

### Вирішення:
* Відмова від розробницьких pay-as-you-go API на користь **використання наявних підписок або безкоштовних лімітів** через локальні RPC/клієнтські обгортки (наприклад, Pi, OpenCode) чи локальні моделі (Ollama).
* Використання **LangGraph** як єдиного локального оркестратора, якому байдуже, де саме крутиться модель (у хмарі за підпискою чи локально), оскільки він керує станом і логікою кроків.

## 3. Компоненти та принципи роботи

### A. Генератор (Основний ШІ на підписці)
* **Принцип:** Замість платних API-ключів, основний генератор працює через локальний клієнт підписки (наприклад, `pi` в RPC-режимі або OpenCode), використовуючи браузерну OAuth-авторизацію користувача.
* **Перевага:** Нуль додаткових витрат на токени, повне використання сплаченої підписки.

### B. Критик (Радник / Аудитор)
* **Принцип:** Використовує безкоштовний тир **Google AI Studio (Gemini Free Tier)** через легкий прямий API-ключ.
* **Перевага:** Жодних щомісячних платежів, безкоштовних лімітів повністю достатньо для регулярних аудиторських перевірок акустичних планів.

### C. Менеджмент контексту (LangGraph Checkpointers)
* Контекст сесії живе не в повітрі, а утилізується через вбудовані **Checkpointers** LangGraph (збереження стану в локальний SQLite/JSON файл у папці проєкту).
* Сесія не обривається при закритті програми: користувач відновлює роботу з тої ж точки, де зупинився.
* **Файли — джерело істини:** Будь-яке рішення записується у `process-state.json` та леджер `v_NNN.json` на диску.

### D. Синхронізація з інтерфейсом (PySide6)
* **Активний канал:** Асинхронний міст через `qasync` та стандартні Qt Signals (`pyqtSignal`) для миттєвої передачі подій графа у вікно чату чи панель завдань.
* **Пасивний канал:** `QFileSystemWatcher` для відстеження змін у файлах, зроблені через термінал або зовнішні інструменти, із можливістю ручного оновлення кнопкою «Оновити».

## 5. План міграції (Roadmap)

1. **Ініціалізація структури проєкту:** Налаштування віртуального середовища Python, встановлення `langgraph`, `PySide6`, `qasync`.
2. **Створення State Schema:** Опис структури даних `process-state.json` у вигляді `TypedDict` для графа.
3. **Реалізація RPC-обгортки:** Підключення основного ШІ через локальний процес підписки (Pi/OpenCode) та настроювання безкоштовного критика (Gemini).
4. **Інтеграція з Qt:** Зв'язування подій графа з вікнами PySide6 через сигнали/слоти та реалізація механізму Human-in-the-Loop (Arbiter) для затвердження кроків.
