# ТЗ ТСС — технічне завдання

> Технічний бік. Продуктове бачення — у `TCC-Concept.md` (без техніки).
> Тут: модель даних, процесор-профілі, інтеграція зі скілом, зберігання,
> відомі виправлення пілоту. Оновлюється по ходу.

Статус: чернетка, накопичується з обговорень.

---

## 1. Процесор-незалежність (жорстка вимога)

Модель даних **не має бути Helix-подібною**. Різні DSP дають різні параметри:

- **Helix DSP Ultra S** — є ярус віртуальних каналів.
- **MUSWAY** (напр. M6v4) — віртуальних каналів **немає взагалі**.

Тому структура має описувати те, що **реально експонує процесор проєкту**.
Рішення — **процесор-профіль на рівні проєкту** (Helix / MUSWAY / …), який
задає, які яруси й параметри існують. Референс-профілі вже є в
`sound_AutoSci/dsp_profiles/` (`helix-dsp-ultra-s.yaml`, `musway-m6v4.yaml`).

---

## 2. Helix — модель каналів (авторитетно; пілот місцями помилявся)

- **Віртуальні канали: 8.** Рекомендовані назви: `VFL, VFR, VRL, VRR, VC, VSW`.
  Параметри: **phase, delay, gain, INV, MUTE, BYPASS EQ**.
  **Кросоверів на віртуальних каналах НЕМАЄ.**
- **Вихідні канали: до 20.**
- **EQ (на кожен канал, обидва яруси): 30 полос.** На полосу: **BYPASS**, тип
  фільтра ∈ `{PK, LSH, HSH, APF1, APF2}`.
- **FX — це параметр, не канал.**
- Усе це **специфіка Helix і залежить від моделі** — трактувати як один профіль,
  не як схему.

### Виправлення пілоту (borg — врахувати при переробці)
Пілотна віртуальна модель — **placeholder із помилками**, не довіряти:
- віртуальний Center має кросовер — прибрати (обнулити);
- FX змодельовано як віртуальний канал — прибрати;
- модель має брати яруси/параметри з процесор-профілю, не хардкодити.

## 3. Зберігання даних (конвенція)

Проблема пілоту: щоб знайти реальний стан, довелось грепати `~/dev` — це не
конвенція. Цільова схема — **один проєкт = одна папка, яку вказує користувач**
(список recent-projects у застосунку), **нуль авто-пошуку по диску**:

```
<project>/
  project.json                 # процесор-профіль, список пресетів, мета
  presets/
    <preset>/
      target.json              # яка цільова крива (назва/референс)
      state/v_NNN.json         # DSP-снапшоти (леджер)
  measurements/                # або вказівник на REW .mdat / captures
```

- Реальні дані проєкту — **завжди поза публічним репо** (приватна папка).
- Публічний репо тримає лише **синтетичні фікстури**.
- Пілот тимчасово сіє в `data/private/state/<preset>/v_NNN.json` (gitignored) —
  замінити на проєкт-папку за схемою вище.

## 4. Інтеграція зі скілом (ключове)

Процес веде скіл `autosound-tuning`, ТСС — його фронт-енд. Отже скіл має
**емітити стан процесу** у формі, яку ТСС читає:

- фази + статуси;
- поточний план (кроки + прогрес), редагований;
- задача на замір: очікуваний номер, перевірка існування, **валідність свіпу**
  (математика аналізу дрейфу — де саме в `rew_tool`, підключити індикатор);
- статус Радника/Критика: який ШІ+модель, час/фаза/крок останнього виклику;
- вибрана цільова крива на пресет.

Це вимагатиме **змін у скілі** (окрема задача). Межа app↔скіл — визначити:
файли-стану, події, чи прямий виклик.

## 4a. AI-діалог — архітектура (координатор-незалежна)

Діалог з ШІ (Generator↔Critic/Advisor↔User) — головне робоче вікно (Concept §2).
Це не термінал у вікні: бекенд рахує, TCC малює нативний UI. Три способи:

- **A. agent-CLI як підпроцес** — TCC драйвить Claude Code (або Gemini CLI /
  Codex CLI) headless; CLI крутить скіл `autosound-tuning` + `rew_tool`. Переюзає
  весь скіл. Мінус: важче зробити справді provider-agnostic.
- **B. агент усередині застосунку** — Claude підтримує напряму: **Claude Agent
  SDK** (Claude Code як бібліотека, in-process), **Tool Runner** (готовий
  agentic-цикл над своїми інструментами), або обгортка над Messages API (tool
  use / MCP-конектор / server-tools). Координатор = Claude.
- **C. provider-agnostic (ціль)** — можливості (`rew_tool`, REW API,
  target-криві, аналіз) за **MCP-серверами**; координатор — **змінний адаптер**
  (`send(messages, tools) → tool-calls/відповідь`), тож Claude / Gemini / інший
  підключається однаково. Знання скіла — **системний промпт + стан-протокол**,
  не зашите в Claude Code.

**Рекомендація:** ціль — **C** (MCP + coordinator-адаптер), бекендиться Claude
зараз (Agent SDK або Tool Runner), Gemini-адаптер пізніше. Швидкий старт — **A**
(Claude Code headless), поки MCP не винесений. Наслідок (узгоджено): **скіл
`autosound-tuning` треба портувати** з Claude-Code-специфічної форми в
портабельну (промпт + MCP-інструменти + стан-протокол).

Довідка Claude-боку (звірено зі skill `claude-api`): Messages API tool use,
Tool Runner, Claude Agent SDK (`claude-agent-sdk`), MCP-конектор, server-tools.
Для in-app агента — дефолт-модель Opus 4.8; Gemini/інші — через MCP + адаптер.

## 5. Модель даних (поточна, пілот)

- `state/dsp_state.py`: `CrossoverLeg`, `ChannelState`, `VirtualChannel`,
  `DspSnapshot`. Завантаження через vendored `PresetHistory` (леджер).
- `core/config.py`: резолвер root/preset (env override + дефолт).
- Пілот-снапшот: FULL-пресет, реальні дані з `sound_AutoSci/dsp_state.md`
  (attested-latest 2026-07-23).

**До переробки:** ввести процесор-профіль; винести яруси/параметри з профілю;
кілька пресетів із власними target; конвенція проєкт-папки (розділ 3).

## 6. Стек / межі (з kickoff-бріфу)

- Python + PySide6, `pyqtgraph` для кривих (коли дійде).
- `rew_tool` — vendored submodule; пізніше pip-пакет `autosound-core`.
- **Read-only v1**, жодного авто-запису в DSP до закриття safety-гейтів.
