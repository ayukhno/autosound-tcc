# Harness spike — передача справ

Зібрано 2026-08-04 наприкінці сесії в Cowork. Читати цілком перед першою дією: тут і рамка
рішення, і те, що вже доведено з цифрами, і рівно те місце, де ми зупинилися.

**Мета розслідування.** Замінити `Claude Agent SDK` у головному діалоговому вікні TCC так, щоб
збалансувати три осі:

* **(а) прозорість** — робота з різними ШІ з урахуванням ліцензій і того, що є в користувача;
* **(б) детермінізм** — стабільність даних скіла й передбачуваність процесу;
* **(в) візуалізація** — рольовий діалог (Оркестратор / Радник / Арбітр, аналіз → дія), а не
  потік токенів із «сміттям».

Кандидати: **OpenCode** (`opencode-ai` 1.18.11) · **omp** (`@oh-my-pi/pi-coding-agent` 17.2.5) ·
**LangGraph** (пропозиція в `docs/TCC-Proposal_LangGraph.md`).

---

## 1. Рамка, на яку домовились

Три осі мають **різних власників** — тому один інструмент їх не балансує, і шукати такий не треба.
Їх розділяють:

| Шар | Питання | Рішення |
| :-- | :-- | :-- |
| Рендер | чому діалог виглядає як каша | журнал як транскрипт (див. §2.4) — знімає (в) з-під вибору харнеса |
| Агентний цикл | хто виконує скіл | харнес (OpenCode / omp), не власний граф |
| Стан процесу | фази, чекпоінти, HITL | наглядач у TCC; LangGraph — можливий наступник, не старт |

**По осі (а)** лінія така: **TCC не тримає креденшлів** — він дзвонить у сесію або запускає процес,
якими володіє користувач. Звідси випливає, що внутрішньопроцесна оркестрація (LangGraph усередині
TCC) суперечить позиції, бо ключ тоді тримає TCC. Підтвердилось емпірично: OpenCode **не пропонує**
входу через підписку Claude — тільки API-ключ; для OpenAI та GitHub Copilot підписковий OAuth є.
Наслідок, який варто тримати в голові: дефолтний шлях більшості користувачів веде **не** до Claude,
а скіл писався під Claude. Тому що більше процесу тримається кодом, то дешевша модель прийнятна.

**По осі (б)** детермінізм уже частково в коді скіла (`apply.propose`, `step_done` вимагає evidence,
`eq_gate`). Діра одна: ніщо не змушує оркестратора викликати `enter-phase` / `add-step` / `done`.
Реальні прогони (§3) показали, що діра глибша, ніж «модель лінується». Тому наглядач формулюється
сильніше — **TCC має подавати готовий інструмент запису через MCP, а не змушувати агента шукати CLI
по диску**.

> **Виправлення (2026-08-04, після трьох прогонів).** Ранішня редакція цього документа
> стверджувала, що «`report_phase` на цій поверхні вже є». **Це хибно.** Докстринг `report_phase`
> каже дослівно *This records nothing*, і записувача журналу на MCP-поверхні TCC **немає взагалі** —
> жоден інструмент не пише `journal.jsonl` через TCC. Вимога сформульована правильно, але **не
> виконана**: це не наявна можливість, а найбільший пункт роботи, що випливає з розслідування.
> Втішне — та сама сесія довела, що схема робоча: профіль DSP пройшов повний шлях через MCP
> (`check_existing_profile` → 11× `save_profile_field` → `finalize_profile` → `dsp_profile.json`).

**LangGraph** — не третій кандидат у тому ж ряду, а розвилка. Його чекпоінтер став би **третім**
джерелом істини поряд із `process-state.json` і леджером, при тому що у скіла правило «машинні
файли виграють». Виправданий пізніше, як зовнішній цикл над харнесом, коли наглядач переросте
прості інваріанти. Не з нього починати.

**Схиляємось до OpenCode.** Дві переваги, що важать: інструменти TCC потрапляють у список функцій
моделі як `tcc_*` (скіл каже «виклич `get_tcc_state`» — працює дослівно), і HTTP+OpenAPI переживає
перезапуск TCC, а stdio-процес ні. Ціна: доведеться писати ще й `opencode.json` (рядок у
`write_mcp_config()`), і теза «один `.mcp.json` на будь-який CLI» для фронт-енда B розпадається.

> **Скасовано того ж дня — §5-bis.** Обидві переваги виявились слабшими, ніж записано: видимість
> інструментів в omp вмикається рядком конфігу (`tools.xdev=false`), а вирішальною виявилась вісь,
> по якій я тут не ранжував узагалі — **OpenCode не вміє витратити підписку Claude** (тільки
> API-ключ), і його безкоштовні моделі до скіла не доходять. Фіналіст: omp для не-Claude, Agent SDK
> для Claude.

## 2. Що доведено — з доказами, не з документації

### 2.1 Обидва харнеси проходять два блокери

Стенд: справжній `core/mcp_server.py` headless + стаб замість моделі (`spike/serve_tcc.py`,
`spike/stub_llm.py`), тож без ключів і без витрат.

| | omp 17.2.5 | OpenCode 1.18.11 |
| :-- | :-- | :-- |
| конфіг MCP | читає `.mcp.json` TCC як є | тільки `opencode.json` (`mcp.<name>`, `type: remote`) |
| заголовок `X-TCC-Token` | проходить | проходить |
| інструменти TCC для моделі | `discoverable` під `xd://` — **не** у списку функцій | топ-рівень як `tcc_*`; модель викликала `tcc_copy_helix_eq` напряму |
| гейт вбудованих інструментів | `extension_ui_request` (stdio, `--mode rpc-ui`) | `permission.asked` (SSE) + `POST /permission/{id}/reply` |
| блокування до відповіді хоста | так, 6 с із 6 | так, 6 с із 6 |
| словник відповіді | Approve / Deny | `once` / `always` + запропонований патерн |
| транспорт хоста | stdio NDJSON | HTTP + SSE + OpenAPI |

> **Уточнення, яке легко переплутати.** Дозволи в OpenCode **за замовчуванням не гейтяться**
> (`permission: null`, черга `/permission` порожня). Але **здатність** доставити запит зовнішньому
> не-Node хосту й заблокувати агента доведена: з `"permission": {"bash": "ask"}` в `opencode.json`
> запит прилетів на 1.85 с, Python-хост відповів на 7.89 с, інструмент завершився на 7.94 с.
> «Не гейтить за замовчуванням» ≠ «не вміє». Для TCC це рядок конфігу.

### 2.2 Найважливіше з усього стенду

У прогоні OpenCode модель викликала `tcc_copy_helix_eq`, і інструмент блокувався рівно на `HOLD_S`
— спрацював **гейт усередині самого інструмента** (`mcp_server._confirm()` →
`bridge.request_confirmation()`), а система дозволів харнеса до цього не залучалася.

Отже для інструментів TCC гейт Арбітра **вже харнесо-незалежний**. Від харнеса потрібно лише
вміння віддати назовні дозвіл на **свої власні** вбудовані (bash/edit/write) — це вміють обидва.

### 2.3 Вартість контексту

Стенд (справжній скіл встановлено, стаб замість моделі, до початку розмови):

| | OpenCode | omp |
| :-- | --: | --: |
| запит цілком | 35.4 КБ | 72.5 КБ |
| системний промпт | 11.3 КБ | 29.4 КБ |
| схеми інструментів (11 шт.) | 22.8 КБ | 40.7 КБ |

omp удвічі важчий; у його промпті самих лише згадок `xd://` сорок — те саме рішення, що ховає
інструменти TCC від моделі, коштує ще й контексту.

**У бойовому оточенні (машина Олександра) підлога ще вища: ~20 500 вхідних токенів до першого
слова**, бо OpenCode бачить **64 скіли** з `~/.claude/skills/` і піднімає **45 плагінів**.
`tuning_session.py` це вже вирішив для SDK (`setting_sources=["project"]`, `skills=[SKILL_NAME]`) —
**еквівалент для OpenCode ще не знайдено, і це відкрита задача.** Побічно: OpenCode робить окремий
виклик моделі на генерацію заголовка треду (≈2.5 КБ) — для TCC чистий шум, вимкнути.

Скіл підхопився в обох однаково правильно — прогресивним розкриттям із `.claude/skills/`
(OpenCode: `<available_skills>` + інструмент `skill`; omp: `skill://<name>`), інлайну немає.

### 2.4 Діалог рендериться з журналу, не з потоку токенів

`spike/render_dialog.py` збирає рольову стрічку з `process/journal.jsonl`. Прапорець
`--events-only` доводить головне: **історія читається повністю без жодного слова прози** — видно
фазу, ситуативний крок, незгоду Радника з вендором і моделлю, `config_change` із тим, що він
інвалідував, другу спробу кроку і закриття з evidence. Готові приклади: `spike/out-dialog.html`,
`spike/out-events-only.html`.

Наслідок: **вибір харнеса не впливає на вигляд діалогу.** Проза — гарнір, який TCC зливає за часом.

Під час збирання виявилось, чого журналу бракує для повної картки — звідси SCR-026 і SCR-027 (§5).

**Підтверджено на реальних даних** (2026-08-04): `spike/out-real-EPY.html` — перший рендер із
журналу, який написав справжній агент, а не фікстура. 11 чіпів, фаза −1, сім кроків плану, два
закриті з evidence. Одна правка знадобилась: справжній скіл пише поле **`step`**, фікстура вгадала
`id` — `render_dialog.py` тепер приймає обидва.

### 2.5 У OpenCode два зворотні канали, а не один

Крім дозволів є **канал питань до користувача**, і його знайшли тільки в реальному прогоні:

```
GET  /question                 черга
POST /question/{id}/reply      відповідь хоста
POST /question/{id}/reject
SSE: question.asked · question.replied
```

Claude поставив три питання **структуровано** — з варіантами й описами, — і хід **блокується**,
доки хост не відповість. Gemini те саме питав прозою й завершував хід: канал модельозалежний, але
поверхня є.

Два наслідки для TCC. **Практичний:** цей канал треба обслуговувати, інакше вікно виглядає
зависшим — це те саме, що ми бачили як «десять хвилин мовчання», тільки з іншого боку. Із 1714 с
ходу на Claude **1225 с** — чекання на людину; оптимізувати нема чого, але очікування має бути
читабельним: видно, хто на кого чекає. **Концептуальний:** взаємодія «Арбітр вирішує» приходить
**структурою**, а не прозою, тобто лягає в рольовий діалог як дані. Це **четверте** джерело стрічки
поряд із прозою Оркестратора, подіями журналу й Радником (§2.4).

## 3. Три реальні прогони — результати

Один проєкт, один нейтральний промпт, змінюються тільки модель і наявність MCP-сервера TCC.

| | 1. Gemini без TCC | 2. Gemini з TCC | 3. Claude Opus 5 з TCC |
| :-- | --: | --: | --: |
| час ходу | 320 с | 100 с | 1714 с (з них ~1225 с чекання на людину) |
| викликів інструментів | 6 | 13 | ~30 |
| `tcc_*` викликано | — | 4 | 8 різних, 20+ викликів |
| **подій у журналі** | **0** | **0** | **11** |
| пошук `rew_tool` по диску | ні | ні | ні |
| токени ходу | 40 870 | 40 290 | 83 604 |

### Головний висновок: детермінізм тримається на моделі, а не на коді

Журнал з'явився **лише** на Claude — і **не через MCP**, а через bash:

```
python3 .claude/skills/autosound-tuning/rew_tool/state/process.py ./process enter-phase -1
python3 … ./process add-step lang "Set session language"
python3 … ./process done lang "user-answer …"
```

Причина не в старанності. Claude **мовчки обійшов обидва дефекти скіла**: написав `python3` замість
приписаного `python` (SCR-028) і сам зарезолвив `.claude/skills/…` замість мертвого
`file:///skills/…` (SCR-029). Gemini спіткнувся на обох — двічі, з TCC і без.

**Отже розрив Claude ↔ Gemini — це не «хто краще слухається скіл», а «хто латає його дірки власним
коштом».** Для продукту це неприйнятно: не можна закладатися, що користувач узяв Opus. SCR-028 і
SCR-029 з «варто зробити» стають **блокуючими** — вони перетворюють везіння на гарантію.

### `tcc_*` тим часом зробили іншу роботу — і зробили її добре

`check_existing_profile` → 11× `save_profile_field` → `finalize_profile` → на диску
`dsp_profile.json` (schema 3, contract-valid). Профіль пройшов повний шлях через MCP і гейти TCC,
без bash. Це доводить, що **та сама схема для запису процесу спрацює** — її просто ще не збудовано
(див. виправлення в §1).

### Дірка наглядача видно в одному рядку реальних даних

`process-state.json` після ходу на Claude:

```
lang        done         ev: ['user-answer 2026-08-04: Ukrainian (session), English (skill issues)']
dspprofile  done         ev: ['TCC bundled exact match: Audiotec-Fischer / Helix DSP Ultra S', 'dsp_profile.json']
interview   in_progress  ev: []      ← відповіді вже в autosound_context.md
reviewer    todo
glossary    todo
install     todo
projfiles   todo
```

**Читати це треба обережно — тут легко звинуватити не того.** Відкритий `interview` — не недогляд:
модель обґрунтувала його явно («не позначаю done, бо ключові факти ще невідомі, а гейт і так не
пропустить done без доказів»), і це правда — крок пакує мову, цілі, місце, авто, драйвери й Fs, а
авто з драйверами ще не названі. Наглядач, який закрив би цей крок, був би шкідливим.

Справжня діра поруч і вужча: **відповіді, які вже прийшли, ніде не записані як події.** Користувач
відповів на шість питань, журнал виріс на 11 подій, і жодна не фіксує відповідь. Дві з них — довгі
інженерні обмеження (референсне місце = водій; перемір базлайну на 96 кГц, що робить недійсними
наявні 12 МБ). Живуть тільки прозою. Словник SCR-004 описує ходи Генератора і виклики Критика —
ролей три, і третя сліду не лишає. Звідси **SCR-030**.

Артефакти на диску: `process/journal.jsonl` (11 подій), `process/process-state.json`,
`dsp_profile.json`, `autosound_context.md`.

### Три дефекти скіла, знайдені першим прогоном

Жоден **не в харнесі** — усі в скілі, тобто відтворяться на будь-якому координаторі:

1. **`python` не існує.** SKILL.md приписує `python rew_tool/...` у **шести** місцях. На стоковому
   маку є тільки `python3` → `zsh:1: command not found: python`. Під Claude Code це було невидимо,
   бо в шелі розробника `python` випадково є (venv / pyenv / Homebrew).
2. **Скіл не може знайти сам себе.** У SKILL.md **47** посилань `file:///skills/autosound-tuning/…`
   — адресація Claude Code, яка більше ніде не означає нічого. Модель пішла шукати через
   `find . -name rew_tool -type d`, а `find` не заходить у симлінк; вибралася лише скануванням
   усього `$HOME`. Близько трьох хвилин втрачено.
3. **Вигаданий сабкоманд** `project.py . init` → дамп usage. Наслідок перших двох: документації
   інструмента з позиції моделі не видно.

**Як це читати.** Порожній журнал тут **не** доводить, що скіл не примушує писати — модель не
змогла дотягтися до записувача. Дві причини треба розділяти, і саме для цього потрібен другий
прогін із піднятим MCP-сервером TCC.

**Ще один результат, який легко не помітити:** перший контакт зі скілом зайняв понад десять хвилин
мовчання. У вікні TCC це виглядало б як зависання. До вимог (в) додається **видимий прогрес по
кроках**, а не мовчазний спінер.

зупиняються користувачем; нічого фонового лишатися не має.

**`spike/real_turn.py` був змінений термінальною сесією** — додано `--timeout` (дефолт 1800 с) і
опитування сесії, якщо POST відвалився по таймауту, бо саме це знищило перший замір. Зміни коректні,
але врахуй, що файл новіший за опис у §6.

## 5. Фіналіст і що робити далі

> **Рішення переглянуто того ж дня.** Редакція вище по тексту називала фіналістом **OpenCode**.
> Це рішення **скасовано**, і причина не в новому вимірі, а в тому, що я ранжував не по тій осі.
> Читати §5-bis нижче; §5 як список робіт лишається чинним, бо він майже весь харнесо-незалежний.

### 5-bis. Чому не OpenCode

Ціль розслідування — не «найкращий агентний цикл», а **інструмент, який не змушує платити за
токени пооперацінно**: максимально використати підписки й безкоштовне. По цій осі:

* **OpenCode не вміє витратити підписку Claude** — Anthropic там тільки по API-ключу (зміряно). Усі
  чотири прогони §3 йшли на pay-as-you-go ключах, тобто рівно тим шляхом, якого треба уникнути.
* **Безкоштовний шлях провалено, і це замір.** `opencode/*-free` — шість моделей без креденшлів
  узагалі. `nemotron-3-ultra-free` (1M контексту): два `ls`, 12.7 с, скіл не відкрито, тексту нема.
  `north-mini-code-free`: скіл підняла, 30 викликів, вилізла за межі проєкту в сусідню теку й
  зависла на одному `read`. Журнал у обох — нуль.
* Підписок OpenAI/Copilot у користувача немає, тож підписочної осі в OpenCode не лишається взагалі.

Дві причини, за якими OpenCode стояв вище omp, розсипались при перевірці:

| | omp дефолт | `tools.xdev=false` | `xdevInlineDevices` |
| :-- | --: | --: | --: |
| інструментів моделі | 11 | 39 | 11 |
| TCC у списку | немає | **усі 20**, `mcp__tcc_*` | немає |
| схеми, байт | 49 065 | 79 190 | 49 065 |

`xd://` — **рядок конфігу**, не архітектура; його власний опис закінчується словами *"Disable to
expose every enabled tool top-level"*. Подвоєння промпту з §2.3 міряне на дефолті, де інструментів
TCC у списку нема взагалі; з них самих — 14 462 байти, решта приросту чужа. Варіант `xdevInline
Devices` не працює: інлайнить **доки** пристрою, не інструменти.

### 5-ter. Фіналіст: omp для не-Claude, Agent SDK для Claude

omp проходить усі чотири перевірки: MCP через `.mcp.json` як є · гейт із зовнішнім не-Node хостом
(«Allow tool: `mcp__tcc_copy_helix_eq`» → хост відповідає на 6-й с → інструмент завершується ще
через 5.02 с, і це `HOLD_S` **власного** гейта TCC — обидва спрацювали послідовно) · інструменти
верхнього рівня · **структурований канал питань** (`ask`: `questions[]` з `options[{label,
description}]`, «Other» додається сам, хід блокується до відповіді хоста).

**Прогін на реальній моделі (Gemini 3.1 Pro через omp, той самий проєкт і промпт).** Скіл
підхопився через `skill://autosound-tuning` + точкові `references/…`; пошуку по диску нема, `python`
не запускався; `mcp__tcc_get_tcc_state` / `check_existing_profile` / `get_capability_checklist`
викликані на ім'я; `dsp_profile.draft.json` створено. **Журнал: нуль подій** — `report_phase` цього
разу не покликано, отже й попередження «call enter_phase», яке в прогоні на OpenCode дало 0 → 1, не
прозвучало. Обидва результати n=1, і разом вони кажуть одне: **записувач доступний, але ніщо не
змушує ним скористатися** — наглядач (п. 3) потрібен незалежно від харнеса.

**Податок, якого в OpenCode не було:** Gemini двічі назвала інструмент як
`functions:mcp__tcc_check_existing_profile`, omp відбив (`Tool … not found`), модель оговталась
чистим іменем. Два згорілі виклики; на слабших моделях коштуватиме більше.

**Ліцензія — і чому «перемикач» її не знімає.** omp має broker із `anthropic (Claude Pro/Max)`,
`openai-codex`, `github-copilot`, `cursor` + локальні раннери. Ганяти підписку Claude через сторонній
клієнт — питання умов Anthropic, і **наявність SDK як запасного шляху ризик не мінімізує**: ризик
виникає в момент, коли TCC *постачає* цей шлях у списку моделей чи в майстрі. Тому поділ **за
провайдером**, а не за перевагою:

* **Claude** — тільки Agent SDK, що запускає **власний CLI користувача**. Код уже є, ліцензійно чистий.
* **Усе інше** (Gemini, локальні, чужі підписки в чужому broker) — через omp.
* TCC **не налаштовує** Anthropic-OAuth в omp, не згадує його в UI, не веде до нього майстром.
  Рядок §1 «TCC не тримає креденшлів» тримається лише разом із «і не скеровує».

**Ціна рішення відома.** SDK живе у трьох файлах — `core/agent_session.py` (265), `core/tuning_
session.py` (309), `tuning_session_cli.py`; `core/mcp_server.py` (735 рядків з інструментами й
гейтом) про SDK не знає нічого. Радник уже вендоронезалежний: `core/critic.py` (251) запускає
`scripts/autosound_ai.py` окремим процесом і підмінює модель через `GEMINI_CRITIC_MODEL`. Тобто
переносити треба **шар сесії**, і його роблять інтерфейсом із двома реалізаціями — `tuning_session.py`
не викидається.

### Своє, у TCC — за спаданням важливості

1. ~~**Записувач процесу на MCP-поверхні.**~~ **Зроблено** (`core/process_writer.py` + шість
   інструментів: `enter_phase` / `add_step` / `start_step` / `finish_step` / `skip_step` /
   `block_step`). Форма — як `profile_writer`: `sys.executable` замість голого `python` і
   `vendor_loader` замість адреси, зрозумілої одному харнесу, тож SCR-028 і SCR-029 на цьому шляху
   не діють. Гейт лишився у скіла: `finish_step` без evidence відхиляється, формулювання
   повертається дослівно.
2. **Шар сесії як інтерфейс** із двома реалізаціями (SDK · omp) — див. 5-ter.
3. **Наглядач**, що заводить план фази й закриває крок проти evidence. Після п. 1 це вже окреме
   питання, а не змішане з доступом: два прогони показали 1 і 0 подій там, де шаблон фази дає сім.
4. **Обслуговування каналу питань** — в omp це `ask` (кадр `select` по stdio, живе рівно стільки,
   скільки сесія), в OpenCode був HTTP-чергою. Без цього вікно виглядає зависшим.
5. **Замкнути область на проєкт.** В omp із `xdev=false` у `rpc-ui` каталог роздувся до **203**
   інструментів — затягло всі MCP-сервери користувацького конфігу. Це те саме, що 64 скіли + 45
   плагінів в OpenCode, тільки гірше, і без цього вимкнення `xdev` з'їдає те, заради чого робилось.
6. **Рендер із журналу** підключити до `dialog_panel.py` замість `mock_data.DIALOG`.
   Доведено на реальних даних: `spike/out-real-EPY.html`.

### У скіл

SCR-028 і SCR-029 (§6) стали **блокуючими**: без них скіл працює лише на моделях, які самі
здогадаються обійти його дефекти. Решта — за списком у §6.

### Якщо треба повторити прогін

Тека `testTCC-EPY` уже не чиста (§4) — для нової базової лінії відкоти `process/`,
`dsp_profile.json`, `autosound_context.md`, `opencode.json` або візьми свіжу теку. Команди:

```
cd <project> && export GOOGLE_GENERATIVE_AI_API_KEY="$GEMINI_API_KEY" && opencode serve --port 4096
# з TCC: ./spike/run_with_tcc.sh <project> ; рестарт serve ; curl -s :4096/mcp

  --prompt "Start a tuning project here. Read what is on disk first, then tell me where we are and what the next step is."

```

Промпт навмисно **нейтральний**: підкажеш «запиши фазу» — зміряєш промпт, а не скіл.

## 6. Заявки в скіл, підняті цією сесією

Усі в `docs/SKILL-CHANGE-REQUESTS.md` (нумерація з 026 — 020…025 зайняті на `feat/installer`):

| SCR | Про що |
| :-- | :-- |
| **026** | `apply.propose` кладе поруч зі знімком **дельту** (`was` → `value` + `eq_gate`). Без неї картку аркуша нема з чого малювати, а модель **перенабирає** пораховані числа — транскрипційна поверхня без гейта. |
| **027** | `critic_called` посилається на **текст** критики (`process/reviews/<ts>-<role>.md`). Зараз подія несе вендора, модель і outcome — досить для чіпа, нічого для бабла. |
| **028** | Приписані команди не мають викликати голий `python` — шість місць, мертві на стоковому маку. Краще резолвлений інтерпретер із проєкту (інсталятор і так будує venv), гірше — `python3`. |
| **029** | Портабельна самоадресація замість `file:///skills/…` (47 посилань). Це вимірювана форма «портації скіла», яку ТЗ §4a називала абстрактно. |
| **030** | Відповіді Арбітра — не події. Шість відповідей користувача, 11 подій журналу, жодна не фіксує відповідь; дві з них в'яжуть пізні фази (референсне місце; перемір на 96 кГц). Просить подію `user_decision` з `invalidates`, сабкоманду в `process.py` і правило «записати, перш ніж діяти». Під OpenCode дешево: канал `question` віддає обраний label, машинна форма вже є в момент відповіді. |

**028 і 029 — блокуючі.** Решта — за пріоритетом.
